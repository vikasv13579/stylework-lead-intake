## Development Approach

This project was built using an **agentic AI-assisted workflow** where the AI coding assistant acted as a pair programmer across 7 structured phases. The human engineer (user) provided requirements, reviewed outputs, and made architectural approval decisions at each phase gate.

### Phased Development Process

| Phase | Description | Human Input | AI Output |
|---|---|---|---|
| **Phase 1** | Project scaffolding, Docker Compose, Express/Vite setup | Requirements + stack approval | Full project skeleton, Dockerfiles, package configs |
| **Phase 2** | PostgreSQL schema, Prisma ORM, migrations, seed data | Schema review + approval | `schema.prisma`, migrations, `seed.ts`, DB health checks |
| **Phase 3** | Meta Ads webhook ingestion, validator, normalizer | API contract review | `webhook.validator.ts`, `webhook.service.ts`, `lead.repository.ts` |
| **Phase 4** | Lead REST API (CRUD), service + controller layers | Endpoint design approval | Full REST API, Zod validators, lead service, route wiring |
| **Phase 5** | Status workflow state machine, transition endpoint | State machine diagram review | `workflow.service.ts`, `ALLOWED_STATUS_TRANSITIONS`, 422 enforcement |
| **Phase 6** | Frontend Lead Dashboard (React + Tailwind v4) | Design direction | All UI components, React Query hooks, dashboard page |
| **Phase 7** | Integration tests, Prisma mock, E2E wiring | Test coverage scope | `api.integration.test.ts`, `workflow.test.ts`, `__mocks__/prisma.ts` |

## Architecture Decisions

### 1. Layered Architecture (Controller → Service → Repository)
**Decision:** Strict three-layer separation.  
**Reasoning:** Keeps business logic (service), data access (repository), and HTTP (controller) independently testable. The state machine lives entirely in the service layer and can be tested without HTTP or DB.

### 2. State Machine for Status Transitions
**Decision:** Explicit `ALLOWED_STATUS_TRANSITIONS` map with `validateStatusTransition()`.  
**Reasoning:** Business rules for lead lifecycle are non-trivial. Encoding them explicitly prevents accidental data corruption (e.g., re-opening a Converted lead). Returns `422 INVALID_STATUS_TRANSITION` with a clear message.

### 3. Idempotent Webhook Endpoint
**Decision:** Check `externalLeadId` uniqueness before creating; return `200` if duplicate.  
**Reasoning:** Meta Ads webhooks can be retried. Without idempotency, a single lead could be duplicated many times. The DB unique constraint + application-level check provides defense-in-depth.

### 4. Atomic Lead + Activity Creation
**Decision:** Use `prisma.$transaction()` to write Lead + initial Activity in one transaction.  
**Reasoning:** Prevents a lead existing without any audit trail — the audit record is the source of truth for "when was this lead first seen."

### 5. Prisma ORM over Raw SQL
**Decision:** Prisma v5 with PostgreSQL.  
**Reasoning:** Type-safe query builder, automatic migration management, excellent DX. The trade-off (slight overhead vs. raw SQL) is acceptable for this use case.

### 6. React Query for Frontend State
**Decision:** `@tanstack/react-query` for all API interactions.  
**Reasoning:** Provides automatic caching, background refetch, optimistic updates, and loading/error states without manual `useEffect` boilerplate. Mutations automatically invalidate relevant query caches.

### 7. Mocked Prisma in Integration Tests
**Decision:** Use Jest `moduleNameMapper` to swap `src/lib/prisma` with `tests/__mocks__/prisma.ts`.  
**Reasoning:** Allows the full HTTP request → controller → service → repository chain to be tested without a live database. Fast, deterministic, and CI-friendly. The trade-off is reduced coverage of actual SQL behavior.

### 8. Nginx as Production API Proxy
**Decision:** nginx proxies `/api/` and `/webhook/` to the backend container by internal Docker hostname (`backend:4000`).  
**Reasoning:** In development, Vite's dev server handles proxying. In production, Vite is replaced by a static nginx server, so the proxy must be replicated in `nginx.conf`. This was identified as a production bug and fixed after deployment.

## What I Would Do Differently

1. **HMAC verification** for the Meta webhook (requires actual Meta credentials)
2. **Redis idempotency cache** in front of the DB check to reduce load under high replay scenarios
3. **Event queue** (BullMQ) for async webhook processing to decouple ingest latency from DB write latency
4. **CI/CD pipeline** with GitHub Actions running tests on every PR
5. **Playwright E2E tests** covering the full browser → API → DB flow
